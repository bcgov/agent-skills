Frequently Asked Questions

If the answer you're looking for isn't here, the source-of-truth pages are: Consume a Skill, Contribute a Skill, the spec, and Pipeline & governance.

What exactly is a "skill"?

A skill is a small, focused Markdown document — SKILL.md — that teaches an AI coding agent when to act, what to do, and what to avoid. Each skill targets one specific situation (e.g., "adding subnets inside an existing VNet") rather than trying to cover a whole topic.

The format is interoperable with GitHub Copilot, Claude, and other agents that load SKILL.md manifests. See agentskills.io for the broader ecosystem and our spec for the exact rules this repo enforces.

Why does this repo only host BC Gov–specific skills?

Generic skills — Azure SDKs, Microsoft Foundry, M365, document formats, language workflows — are already maintained in larger upstream catalogues (listed on Contribute). Duplicating them here would fragment the ecosystem and double the maintenance cost without giving consumers anything they couldn't already get.

What's missing upstream is the BC Gov–specific layer: Public Cloud Landing Zone constraints, internal services, policy-driven workflows, organisational conventions. That's the gap this repo fills, and the bar we apply when reviewing new skills.

Why GitHub Packages and not public npm?

Three reasons:

  • Scoped to the org. The @bcgov scope on GitHub Packages lives inside the same GitHub org that owns the repo — same access surface, same audit log, same identity. Public npm would introduce a second account, a second set of tokens to rotate, and a second place secrets can leak.
  • Token-free CI. Workflows in this org can publish and consume with the built-in GITHUB_TOKEN. No bot account, no NPM_TOKEN secret to manage.
  • Right audience. These skills encode BC Gov rules — they aren't designed for general public consumption. Hosting them on GitHub Packages signals "made for the org" without forcing the catalog to be private.

Why does installing a "public" package still need authentication?

This is a GitHub Packages behaviour, not a permission on this repo. The npm registry GitHub runs (npm.pkg.github.com) requires a token on every install — even for packages anyone can read. There is no anonymous read path.

The good news is that the token doesn't have to be sensitive: any GitHub user can mint a short-lived one with gh auth refresh -h github.com -s read:packages, and CI gets one for free via secrets.GITHUB_TOKEN. See Consume → Step 2.

Why the GitHub CLI instead of a personal access token?

Both work. The CLI flow is just lower friction:

  • One credential to manage (your gh auth login), not two.
  • Short-lived tokens by default — rotation is automatic when you re-authenticate.
  • gh auth logout cleans up both your CLI session and any NODE_AUTH_TOKEN sourced from it.
  • No "is this PAT still in use anywhere?" graveyard to maintain.

If your environment can't run gh (locked-down CI runner, etc.), a classic PAT with read:packages is a drop-in replacement.

Why doesn't installation use OIDC?

GitHub Packages doesn't accept OIDC for npm reads — only registry tokens. Inside GitHub Actions the built-in GITHUB_TOKEN is already the equivalent of a workflow-scoped, single-job credential, which is the value OIDC would otherwise provide. Outside Actions, the GitHub CLI fills the same role for humans.

If GitHub Packages ever exposes an OIDC-backed npm read flow, we'll switch the docs to it.

Why can't I open a PR from a fork?

The PR workflow has a fork-gate job that fails any PR whose head repo isn't this one. That failure cascades into the results aggregator, which is the required status check on main. The reason: fork PRs would let untrusted code influence what we validate (and, potentially, what we publish). Maintainers re-land fork-style contributions by pushing the change to an in-repo branch after review.

If you don't have push access to bcgov/agent-skills, file an issue describing what you'd like to add. See Pipeline → PR workflow for the full rationale.

Why are signed commits required?

The main branch ruleset requires it. Signed commits give us a verifiable chain of who actually authored each change in the history — useful for audit, for catching compromised credentials, and for keeping the published packages traceable back to a real contributor.

SSH commit signing is the simplest path on a developer laptop. See GitHub's signing docs.

Why didn't my change publish a new version?

The publish workflow skips any version already on GitHub Packages. If your PR edited a skill but didn't bump its package.json version, the merge ran the publish job successfully but no package was uploaded. Open a follow-up PR with npm version patch (or minor/major) inside the skill directory.

See Contribute → Versioning for the full bump flow.

Why isn't there a version in SKILL.md?

Single source of truth. The published version lives in package.json — that's the file npm reads when publishing, and it's the file the publish workflow checks before deciding whether to ship. Duplicating it in the manifest just creates a chance for the two to drift, and a question of which one "wins" when they do. So the spec disallows it entirely.

What are "meta-skills"?

Skills that operate on this repository itself: scaffolding a new skill, validating the spec, releasing a version. They live under .github/skills/ and are validated against the same SKILL.md spec as published skills, but they are not published — they ship with the repo so agents working in a checkout can use them.

My situation isn't BC Gov–specific — where should I look?

Start with the upstream catalogues — they cover most general agent workflows:

  • Microsoft Agent Skills — Azure, Microsoft Foundry, M365, cross-cutting workflows.
  • anthropics/skills — reference skills and the SKILL.md format.
  • awesome-copilot — community-curated index of skills, prompts, and agents.

If something close exists but isn't quite right, an issue or PR upstream benefits the largest audience. See Contribute → Upstream catalogues.
