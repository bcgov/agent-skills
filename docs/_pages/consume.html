Consume a Skill

Skills are published as npm packages to GitHub Packages under the @bcgov scope. Installing one is five steps: configure the registry, authenticate, install, wire the skill into your agent, and (later) upgrade. The SKILL.md format follows the agentskills.io open standard, so the same install flow works for GitHub Copilot, Claude Code, and any other agent that loads SKILL.md manifests.

GitHub Packages always requires authentication, even for public packages on the npm registry. This is a GitHub Packages behaviour, not a permission setting on this repo. The flow below uses the GitHub CLI to mint a short-lived token, so you don't need to manage a personal access token.

Quick install (recommended)

One line. The installer checks for the GitHub CLI (and installs it if missing), adds the read:packages scope, writes the project .npmrc, runs npm install, and offers to wire the skill into your agent (GitHub Copilot, Claude Code, or a custom location for Codex / Cursor / Cline / etc.). Re-run any time to install another skill or upgrade an existing one.

Supply-chain note — pin to an immutable ref in production. The forms below default to main, which is mutable: the installer code can change between when you read it and when you run it. For CI, scripted setup, or any environment where reproducibility matters, replace main with a 40-char commit SHA you have audited — pick the latest green commit from bcgov/agent-skills/commits/main/scripts. This matches the advice our own github-actions skill gives for third-party Actions. 
# macOS / Linux  (interactive prompts work via process substitution)
# Pinned (recommended) -- replace <SHA> with a 40-char commit you have reviewed:
bash <(curl -fsSL https://raw.githubusercontent.com/bcgov/agent-skills/<SHA>/scripts/install-skill.sh)

# Rolling (convenient for one-off installs -- may change without notice):
bash <(curl -fsSL https://raw.githubusercontent.com/bcgov/agent-skills/main/scripts/install-skill.sh)
# Windows (PowerShell)  works on PS 5.1 and PS 7 with no ExecutionPolicy change
# Pinned (recommended) -- replace <SHA> with a 40-char commit you have reviewed:
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/bcgov/agent-skills/<SHA>/scripts/install-skill.ps1)))

# Rolling (convenient for one-off installs -- may change without notice):
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/bcgov/agent-skills/main/scripts/install-skill.ps1)))

Prefer to audit the script before running it? Pin to a SHA, download, read, then run. When you pin to a commit SHA, GitHub serves the exact blob that was committed at that ref — the SHA itself is the integrity anchor; there is no separate published hash to compare against. Recording a sha256sum is useful for your own change-management trail (so re-deploys can detect drift), not as a first-time verification step.

# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/bcgov/agent-skills/<SHA>/scripts/install-skill.sh -o install-skill.sh
less install-skill.sh                              # review the code
sha256sum install-skill.sh                         # optional: record with your deploy ticket
bash install-skill.sh
# Windows (PowerShell)
irm https://raw.githubusercontent.com/bcgov/agent-skills/<SHA>/scripts/install-skill.ps1 -OutFile install-skill.ps1
Get-Content install-skill.ps1 | more               # review the code
Get-FileHash install-skill.ps1 -Algorithm SHA256   # optional: record with your deploy ticket
.\install-skill.ps1

Non-interactive form (CI or scripted setup — passing a positional skill name skips the wire-up prompt automatically):

bash <(curl -fsSL https://raw.githubusercontent.com/bcgov/agent-skills/<SHA>/scripts/install-skill.sh) azure-networking 0.1.1
& ([scriptblock]::Create((irm https://raw.githubusercontent.com/bcgov/agent-skills/<SHA>/scripts/install-skill.ps1))) -Skill azure-networking -Version 0.1.1

Agent compatibility today: only Copilot and Claude Code load SKILL.md natively via the agentskills.io standard. For Codex CLI, Cursor, Cline, Continue.dev, and others, pick “Custom location” in the wire-up prompt and the script symlinks the skill into the folder your tool already scans — see Step 4 for the underlying snippets.

Prefer to understand or run each step yourself? The manual flow follows.

Prerequisites

Install the GitHub CLI once per machine

The local-dev flow uses gh to mint a short-lived NODE_AUTH_TOKEN for npm. See the official install guide.

# Windows (PowerShell)
winget install --id GitHub.cli

# macOS
brew install gh

# Linux — see the install guide for your distro

Then sign in:

gh auth login
gh auth status

You also need Node.js installed; any current LTS works.

Step 1: Point npm at GitHub Packages

Create a project-local .npmrc beside the package.json where you want to consume the skill. The same file works in local dev and GitHub Actions; the only thing that changes is where NODE_AUTH_TOKEN comes from.

@bcgov:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}

${NODE_AUTH_TOKEN} is expanded by npm at install time from the environment variable; the literal string lives in the file, so it's safe to commit.

Step 2: Get a token into NODE_AUTH_TOKEN

Choose the path that matches where you're running npm install.

Local development (GitHub CLI)

First time only, grant your CLI token the read:packages scope:

gh auth refresh -h github.com -s read:packages

When prompted "Authenticate Git with your GitHub credentials?", answer No if you already have Git auth working (especially SSH commit signing). The prompt is unrelated to npm and answering yes can overwrite Git settings.

Every shell session, export the CLI's current token as NODE_AUTH_TOKEN:

# PowerShell
$env:NODE_AUTH_TOKEN = gh auth token

# bash / zsh
export NODE_AUTH_TOKEN=$(gh auth token)

Want to revoke npm access later? gh auth logout ends both your gh session and any NODE_AUTH_TOKEN that came from it, so credential management stays in one place.

GitHub Actions (built-in GITHUB_TOKEN)

No personal token or repo secret to configure. The workflow's automatic GITHUB_TOKEN can read packages as long as the job declares packages: read:

jobs:
  install-skills:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: read
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: "24"
      - run: npm ci
        env:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Step 3: Install

Pick a skill from the catalogue and pin a version for reproducible pulls:

npm install @bcgov/<name>@<version>

Or omit the version to track the latest dist-tag, which the publish workflow updates on every release:

npm install @bcgov/<name>

The package lands at node_modules/@bcgov/<name>/ with its SKILL.md at the root, plus any references/, scripts/, or assets/ the skill ships. The on-disk layout matches the source repo exactly. Step 4 wires that directory into the location your agent already scans.

Validated end-to-end. The flow above was tested against a clean temp directory: npm install exits 0 and the package, its SKILL.md, and any bundled references/ land in node_modules/ as expected.

Step 4: Wire it into your agent

The SKILL.md format is the agentskills.io open standard, so GitHub Copilot, Claude Code, Cursor, and any other compatible agent can load these skills. Because the published package name (@bcgov/<name>) is identical to the manifest name, you have two ways to wire skills in — pick whichever fits your setup.

Option A: Point your agent at the whole @bcgov scope (recommended)

Set the agent's skills location to node_modules/@bcgov/ once. Every installed @bcgov/* skill is auto-discovered, and new installs (or upgrades) are picked up on the next reload — no per-skill wiring, no symlinks to maintain.

// .vscode/settings.json — GitHub Copilot in VS Code
{
  "chat.agentSkillsLocations": ["node_modules/@bcgov"]
}
# Claude Code (project session)
claude --add-dir node_modules/@bcgov

For details on each agent's discovery setting see VS Code Agent Skills and Claude Code skills.

Option B: Symlink one skill at a time

Some agents only scan a fixed project folder. Symlink each installed package in — the folder name matches the package name, so the link is one-to-one with no renaming.

The snippets below assume azure-networking; substitute any @bcgov/<name> you installed.

GitHub Copilot (VS Code)

VS Code Copilot auto-discovers project skills under .github/skills/, .claude/skills/, or .agents/skills/; personal skills live under ~/.copilot/skills/, ~/.claude/skills/, or ~/.agents/skills/.

# bash / zsh (from repo root)
mkdir -p .github/skills
ln -s ../../node_modules/@bcgov/azure-networking .github/skills/azure-networking

# PowerShell (from repo root; symlinks need Developer Mode or admin)
New-Item -ItemType Directory -Force .github\skills | Out-Null
New-Item -ItemType SymbolicLink -Path .github\skills\azure-networking -Target ..\..\node_modules\@bcgov\azure-networking

# Copy instead of symlink (works everywhere, but you re-copy on update)
cp -r node_modules/@bcgov/azure-networking .github/skills/azure-networking

Copilot picks up the skill on the next chat.

Claude Code

Claude Code loads project skills from .claude/skills/ and personal skills from ~/.claude/skills/, and watches the directory so newly linked skills appear in the same session.

# bash / zsh (from repo root)
mkdir -p .claude/skills
ln -s ../../node_modules/@bcgov/azure-networking .claude/skills/azure-networking

# PowerShell (from repo root)
New-Item -ItemType Directory -Force .claude\skills | Out-Null
New-Item -ItemType SymbolicLink -Path .claude\skills\azure-networking -Target ..\..\node_modules\@bcgov\azure-networking

Other agents (Cursor, Claude API, custom loaders)

Any agent that loads SKILL.md manifests directly can point at the installed directory:

node_modules/@bcgov/<name>/SKILL.md

References, scripts, and assets sit next to SKILL.md, so relative links inside the manifest resolve without extra config. For the Claude API Skills beta, pass the same path to the SDK's skill loader; see the anthropics/skills reference repo for the SKILL.md contract and loader examples.

GitHub Actions

If a workflow runs an agent and needs the skill on disk in the agent's expected location, install and link in the same step:

- run: |
    npm ci
    mkdir -p .github/skills
    ln -sf "$(pwd)/node_modules/@bcgov/azure-networking" .github/skills/azure-networking
  env:
    NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Step 5: Upgrade

Skills are plain npm packages, so use the npm commands you already know:

npm outdated @bcgov/<name>        # see what's newer
npm update   @bcgov/<name>        # move within your semver range
npm install  @bcgov/<name>@<version>  # jump to an exact version

Use a semver range (e.g. "^0.1.0") in package.json to pick up compatible updates on npm update, or pin an exact version to freeze it. Your lockfile keeps installs reproducible across the team.

Troubleshooting

npm error 401 Unauthorized

NODE_AUTH_TOKEN is empty or the token doesn't have read:packages.

  • Re-run gh auth refresh -h github.com -s read:packages.
  • Re-export the token in the current shell: $env:NODE_AUTH_TOKEN = gh auth token (PowerShell) or export NODE_AUTH_TOKEN=$(gh auth token) (bash).
  • Confirm echo $env:NODE_AUTH_TOKEN / echo "$NODE_AUTH_TOKEN" prints a non-empty value.
npm error 404 Not Found

The version doesn't exist, or the registry is wrong. Check:

  • The catalogue for the published version.
  • Your .npmrc has @bcgov:registry=https://npm.pkg.github.com.
  • You're running npm install from the directory containing that .npmrc.
npm picks the wrong registry / falls back to npmjs.org

Make sure the scope and the auth line both point at GitHub Packages; they must both be present in .npmrc:

@bcgov:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}

If you also have a global ~/.npmrc with a different registry=, the scoped registry line wins, but the auth line must match the URL of whatever registry actually serves the install.

GitHub Actions: 403 Forbidden when reading the package

Your workflow job is missing permissions: packages: read. The default GITHUB_TOKEN permission profile in many orgs only grants contents: read, so npm gets denied. Add the block in the snippet above to the job (not the workflow root — job-scoped permissions override).

Can I use a personal access token (PAT) instead of gh auth token?

Yes; a classic PAT with read:packages works in place of the CLI-issued token. The CLI flow is just lower friction (no separate token to generate, rotate, or revoke), and gh auth logout cleans up both your CLI session and any token sourced from it.

My agent doesn't see the skill after I linked it in

Both VS Code Copilot and Claude Code require the skill's on-disk folder name to match the name field in SKILL.md exactly. With this repo's @bcgov/<name> convention the names line up automatically, but if you renamed a folder or copied with a different name you'll hit a silent skip.

  • Correct: .github/skills/azure-networking → node_modules/@bcgov/azure-networking
  • Wrong: .github/skills/azure-net (folder name doesn't match the manifest name: azure-networking) → agent ignores the skill

In VS Code, run Chat: Open Customizations and check the Skills tab to see whether Copilot picked it up. In Claude Code, run /skills. If you used Option A (pointed your agent at node_modules/@bcgov) instead of symlinking, you don't need to worry about this at all.
