Consume a Skill

Skills are published as npm packages to GitHub Packages under the @bcgov scope. Installing one is four steps: configure the registry, authenticate, install, and (later) upgrade.

GitHub Packages always requires authentication, even for public packages on the npm registry. This is a GitHub Packages behaviour, not a permission setting on this repo. The flow below uses the GitHub CLI to mint a short-lived token, so you don't need to manage a personal access token.

Prerequisites

Install the GitHub CLI once per machine

The local-dev flow uses gh to mint a short-lived NODE_AUTH_TOKEN for npm. See the official install guide.

# Windows (PowerShell)
winget install --id GitHub.cli

# macOS
brew install gh

# Linux — see the install guide for your distro

Then sign in:

gh auth login
gh auth status

You also need Node.js installed; any current LTS works.

Step 1: Point npm at GitHub Packages

Create a project-local .npmrc beside the package.json where you want to consume the skill. The same file works in local dev and GitHub Actions; the only thing that changes is where NODE_AUTH_TOKEN comes from.

@bcgov:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
always-auth=true

${NODE_AUTH_TOKEN} is expanded by npm at install time from the environment variable; the literal string lives in the file, so it's safe to commit.

Step 2: Get a token into NODE_AUTH_TOKEN

Choose the path that matches where you're running npm install.

Local development (GitHub CLI)

First time only, grant your CLI token the read:packages scope:

gh auth refresh -h github.com -s read:packages

When prompted "Authenticate Git with your GitHub credentials?", answer No if you already have Git auth working (especially SSH commit signing). The prompt is unrelated to npm and answering yes can overwrite Git settings.

Every shell session, export the CLI's current token as NODE_AUTH_TOKEN:

# PowerShell
$env:NODE_AUTH_TOKEN = gh auth token

# bash / zsh
export NODE_AUTH_TOKEN=$(gh auth token)

Want to revoke npm access later? gh auth logout ends both your gh session and any NODE_AUTH_TOKEN that came from it, so credential management stays in one place.

GitHub Actions (built-in GITHUB_TOKEN)

No personal token or repo secret to configure. The workflow's automatic GITHUB_TOKEN can read packages as long as the job declares packages: read:

jobs:
  install-skills:
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: read
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: "24"
      - run: npm ci
        env:
          NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Step 3: Install

Pick a skill from the catalogue and pin a version for reproducible pulls:

npm install @bcgov/skill-<name>@<version>

Or omit the version to track the latest dist-tag, which the publish workflow updates on every release:

npm install @bcgov/skill-<name>

The package lands at node_modules/@bcgov/skill-<name>/ with its SKILL.md plus any references/, scripts/, or assets/ the skill ships. The on-disk layout matches the source repo exactly, so your agent's skills loader can point at the directory with no extra wiring.

Validated end-to-end. The flow above was tested against a clean temp directory: npm install exits 0 and the package, its SKILL.md, and any bundled references/ land in node_modules/ as expected.

Step 4: Upgrade

Skills are plain npm packages, so use the npm commands you already know:

npm outdated @bcgov/skill-<name>        # see what's newer
npm update   @bcgov/skill-<name>        # move within your semver range
npm install  @bcgov/skill-<name>@<version>  # jump to an exact version

Use a semver range (e.g. "^0.1.0") in package.json to pick up compatible updates on npm update, or pin an exact version to freeze it. Your lockfile keeps installs reproducible across the team.

Troubleshooting

npm error 401 Unauthorized

NODE_AUTH_TOKEN is empty or the token doesn't have read:packages.

  • Re-run gh auth refresh -h github.com -s read:packages.
  • Re-export the token in the current shell: $env:NODE_AUTH_TOKEN = gh auth token (PowerShell) or export NODE_AUTH_TOKEN=$(gh auth token) (bash).
  • Confirm echo $env:NODE_AUTH_TOKEN / echo "$NODE_AUTH_TOKEN" prints a non-empty value.
npm error 404 Not Found

The version doesn't exist, or the registry is wrong. Check:

  • The catalogue for the published version.
  • Your .npmrc has @bcgov:registry=https://npm.pkg.github.com.
  • You're running npm install from the directory containing that .npmrc.
npm picks the wrong registry / falls back to npmjs.org

Make sure the scope and the auth line both point at GitHub Packages; they must both be present in .npmrc:

@bcgov:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
always-auth=true

If you also have a global ~/.npmrc with a different registry=, the scoped registry line wins, but the auth line must match the URL of whatever registry actually serves the install.

GitHub Actions: 403 Forbidden when reading the package

Your workflow job is missing permissions: packages: read. The default GITHUB_TOKEN permission profile in many orgs only grants contents: read, so npm gets denied. Add the block in the snippet above to the job (not the workflow root — job-scoped permissions override).

Can I use a personal access token (PAT) instead of gh auth token?

Yes; a classic PAT with read:packages works in place of the CLI-issued token. The CLI flow is just lower friction (no separate token to generate, rotate, or revoke), and gh auth logout cleans up both your CLI session and any token sourced from it.
