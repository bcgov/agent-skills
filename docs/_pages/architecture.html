Pipeline & Governance

How a change moves from a pull request to a published npm package, and the controls that keep that path safe.

Lifecycle at a glance

open PR  →  fork-gate  →  lint-tests  →  skills  →  results  →  ✅ mergeable
                                                          │
                                            merge to main │
                                                          ▼
                                                   publish workflow
                                                          │
                                                          ▼
                                            @bcgov/skill-<name>@x.y.z
                                            on GitHub Packages

PR workflow — .github/workflows/pr.yml

Runs on every pull request with least-privilege permissions (contents: read). Four jobs, three phases — the fourth job aggregates the result.

1. fork-gate

Always runs. Fails the PR if it was opened from a fork — we never spend CI minutes on (or grant any token to) untrusted code. Maintainers re-land fork PRs from an in-repo branch after review. Produces a real failure (not a neutral "skipped") so branch protection can require it.

2. lint-tests

Needs fork-gate. Validates the codebase that produces skills: ruff format --check, ruff check, pytest -q. If the generator/validator itself is broken, validating the skill output is meaningless — so this runs first.

3. skills

Needs lint-tests. Runs the validator against only the skills the PR touched, diffed against the base branch: uv run python scripts/validate_skill.py --base "origin/${{ github.base_ref }}". This is what enforces the SKILL.md spec.

4. results required

Always runs (if: always()), needs every other job, and fails if any of them failed or was cancelled. This is the single required status check on main, so jobs can be added or renamed in the workflow file without touching branch protection. skipped counts as a pass on purpose, so future if:-filtered jobs don't false-fail the gate.

Publish workflow — .github/workflows/publish.yml

Triggered on push to main with the path filter skills/**, so docs-only or workflow-only merges don't run it. The workflow grants packages: write only to this job and uses the built-in GITHUB_TOKEN — no PAT, no org secret.

  1. actions/checkout@v6 with fetch-depth: 0 for the full history.
  2. Install uv (SHA-pinned astral-sh/setup-uv).
  3. Re-validate every skill with uv run python scripts/validate_skill.py --all — last line of defence before bytes leave the repo.
  4. actions/setup-node@v6 targeting Node 24, with registry-url: https://npm.pkg.github.com and scope: @bcgov.
  5. Run .github/scripts/publish-changed-skills.sh, which diffs BEFORE_SHA against HEAD_SHA, walks each changed skill, and runs npm publish with NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}.
Already-published versions are skipped. A merge that doesn't bump a skill's package.json version is a no-op for that skill — re-publishing is impossible by design. Bumping the version is what ships a release. See Versioning.

Dependabot auto-merge — .github/workflows/dependabot-auto-merge.yml

Dependabot opens upgrade PRs for the actions and Python deps; this workflow approves them and enables auto-merge. The actual merge still has to wait for the same results check to go green, so a broken upgrade can't slip through.

  • Trigger: pull_request_target for opened / reopened / synchronize.
  • Guard: if: github.event.pull_request.user.login == 'dependabot[bot]' — only Dependabot's PRs.
  • Concurrency: per-PR group, cancel-in-progress.
  • Steps: gh pr review --approve, then gh pr merge --auto.

Branch protection — main ruleset 17296594

The rules that keep main safe:

ControlSetting
Pull request requiredYes (0 approvals required — review by convention)
Required status checkresults, strict (branch must be up to date with main)
Signed commitsRequired
Code scanningCodeQL — fail on high or above
Force-push to mainBlocked
Delete mainBlocked
Bypass actorsNone

Because the only required check is results, the PR workflow can add, rename, or restructure jobs over time without anyone having to update the protection ruleset.

Action pinning policy

First-party (actions/*)

Pinned to a major version tag — GitHub guarantees those tags forward-only. Easier to read, and Dependabot still bumps majors.

uses: actions/checkout@v6
uses: actions/setup-node@v6

Third-party

Pinned to an immutable commit SHA, with the human-readable version in a trailing comment. Defends against tag-hijack / supply-chain attacks. Dependabot bumps these too.

uses: astral-sh/setup-uv@fac544c07dec837d0ccb6301d7b5580bf5edae39 # v8.2.0

Permissions model

  • PR workflow: top-level permissions: contents: read. Every job is read-only — there is nothing here that needs to write back to the repo.
  • Publish workflow: contents: read + packages: write. The write scope is granted only on the path that actually ships packages.
  • Dependabot auto-merge: contents: write + pull-requests: write. Required to approve and auto-merge — but the merge itself still has to clear the results gate.
