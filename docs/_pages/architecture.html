Pipeline & Governance

How a change moves from a pull request to a published npm package, and the controls that keep that path safe.

Lifecycle at a glance

open PR  →  fork-gate  →  lint-tests  →  skills  →  results  →  ✅ mergeable
                                                          │
                                            merge to main │
                                                          ▼
                                                   publish workflow
                                                          │
                                                          ▼
                                            @bcgov/skill-<name>@x.y.z
                                            on GitHub Packages

PR workflow: .github/workflows/pr.yml

Runs on every pull request with least-privilege permissions (contents: read). Four jobs across three phases; the fourth aggregates the result.

1. fork-gate

Always runs. Fails the PR if it was opened from a fork. We never spend CI minutes on (or grant any token to) untrusted code. Maintainers re-land fork PRs from an in-repo branch after review. Produces a real failure (not a neutral "skipped") so branch protection can require it.

2. lint-tests

Needs fork-gate. Validates the codebase that produces skills: ruff format --check, ruff check, pytest -q. If the generator/validator itself is broken, validating the skill output is meaningless, so this runs first.

3. skills

Needs lint-tests. Runs the validator against only the skills the PR touched, diffed against the base branch: uv run python scripts/validate_skill.py --base "origin/${{ github.base_ref }}". This is what enforces the SKILL.md spec.

4. results required

Always runs (if: always()), needs every other job, and fails if any of them failed or was cancelled. This is the single required status check on main, so jobs can be added or renamed in the workflow file without touching branch protection. skipped counts as a pass on purpose, so future if:-filtered jobs don't false-fail the gate.

Publish workflow: .github/workflows/publish.yml

Triggered on push to main with the path filter skills/**, so docs-only or workflow-only merges don't run it. The workflow grants packages: write only to this job and uses the built-in GITHUB_TOKEN. No PAT, no org secret.

  1. Check out the full history (fetch-depth: 0) so the diff against the previous commit works.
  2. Install uv (third-party action, SHA-pinned per the policy below).
  3. Re-validate every skill with uv run python scripts/validate_skill.py --all, the final check before any package bytes leave the repo.
  4. Set up Node with the registry pointed at https://npm.pkg.github.com and the @bcgov scope. (The exact Node version lives in the workflow file.)
  5. Run .github/scripts/publish-changed-skills.sh, which diffs BEFORE_SHA against HEAD_SHA, walks each changed skill, and runs npm publish --tag latest with NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}. The --tag latest keeps the latest dist-tag pointed at the just-shipped version, so npm install @bcgov/skill-<name> (no version) always pulls the most recent release.
Already-published versions are skipped. A merge that doesn't bump a skill's package.json version is a no-op for that skill, so re-publishing is impossible by design. Bumping the version is what ships a release. See Versioning.

Dependabot auto-merge

Dependabot opens grouped upgrade PRs with Conventional Commit prefixes. Cadence and ecosystems are configured in .github/dependabot.yml. When the PR's author is dependabot[bot], an in-repo workflow approves it and turns on auto-merge, so it squash-merges itself the moment the same results check goes green. If the upgrade breaks something, results stays red and the PR sits there until a human looks at it.

The auto-merge workflow lives alongside the rest of CI under .github/workflows/. The merge gate it has to clear is exactly the one humans clear: there is no special path around results, and the workflow itself only acts on PRs Dependabot opened.

Because the only required check is results, the PR workflow can add, rename, or restructure jobs over time without anyone having to update the protection ruleset.

Action pinning policy

The policy is below; what's actually pinned right now lives in the workflows under .github/workflows/.

First-party (actions/*)

Pinned to a major-version tag. GitHub guarantees those tags forward-only, so a major-tag pin is safe to read. Dependabot still bumps majors.

uses: actions/checkout@v<major>
uses: actions/setup-node@v<major>

Third-party

Pinned to an immutable commit SHA, with the human-readable version in a trailing comment. Defends against tag-hijack / supply-chain attacks. Dependabot bumps these too.

uses: <owner>/<action>@<40-char-sha> # v<version>

Permissions model

  • PR workflow: top-level permissions: contents: read. Every job is read-only; nothing here needs to write back to the repo.
  • Publish workflow: contents: read + packages: write. The write scope is granted only on the path that actually ships packages.
  • Dependabot auto-merge: contents: write + pull-requests: write. Required to approve and auto-merge, but the merge itself still has to clear the results gate.

References in the repo

Everything described above lives in three directories. Trust the directories themselves rather than the file names inside them, so this page doesn't go stale every time a file is added, renamed, or split:

  • .github/workflows/: PR validation, publish-on-merge, Dependabot auto-merge, docs deploy.
  • .github/scripts/: the helper scripts the workflows call, so workflow YAML stays short and reviewable.
  • scripts/: the Python validator and its tests.
